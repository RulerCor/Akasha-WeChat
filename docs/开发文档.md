## 1. 项目全景

### 1.1 它在做什么

把**微信个人号**接进 **AstrBot**（AI 框架），让 AI 以"微信好友/群成员"的身份聊天。

```
微信 PC 客户端  ←──UIA 自动化──┐
   ↑↓                          │
WeFlow(读消息/媒体) ──SSE──→ 桥接(Akasha-WeChat_RC) ──OneBot/WS──→ AstrBot ──→ LLM
```

- **WeFlow**：第三方微信数据服务，只读（SSE 推送新消息 + HTTP 查历史/媒体）
- **桥接（本项目）**：协议转换 + 收发调度 + Web 面板
- **AstrBot**：AI 大脑（人设、知识库、工具、多模态、定时任务）
- **发送**：WeFlow **没有发送接口**，所以发送走 Windows UIA 自动化操作微信窗口

## 2. 快速开始

### 2.1 前置条件

- Windows + **微信 PC 4.x**（必须登录，且**窗口保持打开**——UIA 依赖窗口）
- WeFlow 已运行并拿到 Access Token
- Python 3.11+（桥接与 AstrBot 各有独立 `.venv`）

### 2.2 启动

```bat
:: 桥接
cd runtime\bridge
start.bat            :: 或 .venv\Scripts\python.exe main.py

:: AstrBot
cd runtime\astrbot
start.bat            :: 或 .venv\Scripts\python.exe run_astrbot.py run

:: 模拟器（可选，离线测说话效果）
cd sim
start_sim.bat
```

启动顺序：**WeFlow → AstrBot → 桥接**（桥接有 5 秒自动重连，顺序错了也能自愈）。

### 2.3 停止

直接关窗口即可。若异常退出残留 `bridge.pid`，下次启动会拒绝并提示，删掉再启。

> ⚠️ **由 AI / 脚本启动时务必清空 `PYTHONPATH`**：
> 自动化工具环境里 `PYTHONPATH` 常指向一个注入 `sitecustomize.py` 的 shim 目录，
> 它会拦截 `os.remove()` 并可能以 `SystemExit(1)` 直接杀掉进程
> （AstrBot 清理临时文件时就这样死过一次）。写法：
> `PYTHONPATH= ./.venv/Scripts/python.exe main.py`
> 用户自己双击 `start.bat` 不受影响。

### 2.4 要输 ID 的地方，怎么选？

**结论：视觉化选择统一在桥接面板（8766 →「成员与权限」页）做。**

AstrBot 自带面板（6185）的配置项是**静态 schema + 编译好的 Vue 前端**，
选项无法按"当前已知群"动态生成，所以那里只能是手填 ID。
桥接面板知道所有群，因此把这些字段都做成了**勾选框**：

| AstrBot 字段 | 含义 | 桥接面板位置 |
|---|---|---|
| `platform_settings.id_whitelist` | 平台 ID 白名单 | 「高级」折叠区，勾选 + 自定义条目 |
| `provider_ltm_settings.active_reply.whitelist` | 随机插话白名单 | 「高级」折叠区，勾选 + 自定义条目 |
| `provider_ltm_settings.active_reply.blacklist` | 随机插话黑名单 | **群总表「插嘴」列**（勾=允许，不勾=进黑名单）+ 高级区自定义条目 |
| `admins_id` | 管理员 | 「管理员」列表勾选 |

不在上面的「已知群」里的条目会落到同组的**自定义条目**文本框里保留，不会丢。
（其余带 `list` 的字段如 `pipeline_ids`、`websearch_*_key` 是模型/密钥配置，
不是微信会话 ID，没有"点选"的语义。）

> v1.2.3 起「成员与权限」页改版：**群回复开关 + 插话黑名单合并成一张「群里管什么」总表**，
> 每个群一行两列（回复 / 插嘴）。插话黑名单用**反向表达**（勾 = 允许插嘴），
> 插话**白名单**与平台白名单收进「高级」折叠区。
> ⚠️ 白名单非空时，表格的「插嘴」勾选会被它收紧（面板会显示黄色警示）。
> 面板支持 `#settings` / `#members` 深链，刷新后停留在原页签。

### 2.4 换电脑

整个 `Akasha-Wechat_RC` 文件夹拷过去即可。代码与配置**不写死绝对路径**：
相对路径以「项目根（桥接目录的上一级）」为基准；AstrBot 相关路径留空时会自动搜索
`runtime/astrbot`、`../AstrBot` 等常见布局。唯一需要重新填的是 WeFlow Token。

## 3. 消息全链路

### 3.1 收到消息 → AI

```
WeFlow SSE 推送
  → bridge_core.WeFlowBridge.listen_sse()
  → ignore_reason()          过滤（自己发的 / 语音 / 系统消息 / 已见）
  → add_to_buffer()          按 (会话, 发言人) 缓冲 5 秒，合并同一人的连续发言
      · 群图片：判断是否与"同一个人的 @"同属一次请求，是则并入
      · 记录 mentioned_any（这批里有没有真 @）
  → process_sender()
      · 解析身份：群成员名册 → wxid → user_id = md5(wxid)
      · 构造 OneBot 事件（@ 段仅在本批真 @ 过时才加）
  → ob_client 经反向 WS 推给 AstrBot
```

### 3.2 AI → 发出消息

```
AstrBot 生成回复
  → aiocqhttp 适配器 → send_group_msg / send_private_msg（OneBot 段数组）
  → ob_protocol 逐段处理
      reply → 原生引用（右键原消息→「引用」）或文本前缀
      at    → 当前丢弃（原生引用已表达"回复谁"）
      text  → UIA 发送（引用优先，失败降级普通）
      image → 剪贴板粘贴
      file  → CF_HDROP 剪贴板粘贴
  → state.note_sent_text()   记录已发内容，拦截 WeFlow 回声（防自问自答）
```

## 4. 核心机制

### 4.1 身份与会话 ID（"加一次管理员，处处生效"）

SSE 推送在群里**只给昵称不给 wxid**，早期实现用 `md5(群ID + 昵称)` 生成 user_id，
导致同一个人在不同群/私聊是不同 ID —— 管理员要逐群添加。

现在：启动时拉取所有群成员名册（WeFlow `/api/v1/group-members`），
得到 `昵称 ↔ wxid` 映射，群消息发言人先查名册解析回 wxid：

```
user_id = md5(wxid)          ← 私聊与所有群同一个 ID
```

- 名册每 10 分钟自动刷新；未命中时回退旧方案并记日志
- 群会话仍按 `group_id` 隔离，群聊记忆互不影响
- 面板「成员与权限」勾选管理员 → 写 `data/admins.json` → 同步 UID 到 AstrBot `admins_id`

> ⚠️ `admins_id` 必须是**数字 UID**，填昵称无效（AstrBot 按字符串比较）。

### 4.2 群聊模式

| 模式 | 行为 |
|---|---|
| `all`（标准，默认） | 所有群消息转发给 AstrBot；**@ 必回**；非 @ 由 AstrBot 随机插话决定 |
| `batch` | 把缓冲窗内全群发言合并成一条"对话切片"再发，适合旁听整段讨论 |

> v1.0.0 之前还有 `mention`（仅@回复）。因为 rc.6 修好"假 @ 段"后它与 `all`
> 的唯一区别就是 AstrBot 随机插话开关，已于 v1.2 前合并。
> 老配置里的 `mention` 读取时自动归一化为 `all`。

### 4.3 唤醒与随机插话（主动回复）

三层闸门，配在不同地方：

1. **桥接层** — 控制面板的"群聊模式"；或按群静音（面板「成员与权限」每行的回复开关，
   写 `data/muted_sessions.json`，连 @ 都不回）
2. **AstrBot 唤醒判定** — 收到 `[At:]` 或匹配唤醒前缀才当"叫它了"
3. **随机插话** — AstrBot `provider_ltm_settings.active_reply`

`active_reply` 字段：

| 字段 | 说明 |
|---|---|
| `enable` | 总开关 |
| `possibility_reply` | 命中概率（当前 0.03） |
| `whitelist` | **留空 = 所有群**；填群 ID 或 UMO 则只在名单内插话 |
| `blacklist` | **本分支新增**，优先级高于白名单，名单内绝不插话 |

触发插话还需：非 @ 消息 + 该会话已有对话 + 掷骰命中。
**@ 唤醒的正常回复与此开关无关，永远会回。**

### 4.4 引用回复与 @（⚠️ 当前微信版本做不到原生引用）

AstrBot 开启 `reply_with_quote` 后，回复链开头是 `{"type":"reply","data":{"id":N}}`；
开启 `reply_with_mention` 则带 `{"type":"at","data":{"qq":UID}}` 段。

**2026-09-14 实测结论：当前微信 4.x 的消息右键菜单是自绘的、对 UIA 完全不可见。**
右键 / 鼠标悬浮 / 先左键选中再右键，三种方式探测都**零新增控件、零新增顶层窗口**。
（注意：主窗口里本来就有一个常驻控件叫「引用」，按名字搜会误判成"菜单已弹出"。）

所以 `quote_reply_native`（右键原消息 →「引用」）**默认已关闭**，实现保留在那里，
将来微信版本或 UIA 行为变了可以直接打开再试。

**实际采用的方案**：`mention_as_text`（默认开）——把被丢弃的 `at` 段降级成
文字前缀「@昵称 」，至少让群里看得出这条回复是在回谁。已自带 `@` 或 `@全体` 时不重复加。

> 出站段处理现状：`reply`→按配置降级/忽略；`at`→可选转文字；`text`/`image`/`file`/`face`→正常发送。

### 4.5 图片

- **私聊**：图片始终读取
- **群聊**：图片必须和**同一个人的 @** 属于同一次请求才读取
  （图先发、120 秒内再 @；或 @ 后 20 秒内发图）
- 转交方式：`image_caption_model` **留空**（默认）→ 图片原样作为 OneBot image 段
  交给 AstrBot（`base64://`），由主模型（多模态）或 AstrBot 的"图片转述模型"处理；
  **填了** → 走桥接侧描述（`IMAGE_CAPTION_*`），先转成文字再发
- 单张超过 `image_max_bytes`（默认 8MB）跳过

### 4.6 记忆与上下文（重要）

bot 的记忆分**三层**，全在 AstrBot 侧：

| 层 | 机制 | 配置项 | 现状 |
|---|---|---|---|
| ① 对话上下文 | 最近若干轮原文 | `max_context_tokens`（模型级）+ `max_turns`（兜底） | 64K / 100 轮 |
| ② 压缩摘要 | 超阈值后用 LLM 把旧对话**总结成摘要**，保留最近 15% 原文 | `overflow_strategy: llm_compress` | 已启用 |
| ③ 群消息持久化 | 群消息落库（上限 700 条），bot 有工具 `get_group_message_history` 主动检索 | `group_message_history_enable` | 已启用（已存 400+ 条） |

外加**知识库**（`astr_kb_search`，5 个库）作为静态长期知识。

**⚠️ 关键：为什么用 token 阈值而不是轮数**

早期 `max_turns = -1`（不限制）+ 模型窗口 1M，导致单会话涨到 **122 万 token**，
模型进入"回忆模式"（自说自话翻旧账，见 `日志会诊报告-20260914.md`）。

- `max_turns` 是**硬丢弃**：直接砍掉旧轮次，不作总结 → 会真的忘
- `max_context_tokens` 触发的是 **LLM 压缩**：旧对话被总结成摘要保留 → 不丢语义

所以正确做法是：**让 token 阈值先触发**，轮数只作极端兜底。

当前设置（v1.2.0）：

```
所有文本对话模型 max_context_tokens = 65536   ← 超了就 LLM 总结压缩
compression.max_turns              = 100     ← 兜底，正常不会触发
compression.overflow_strategy      = llm_compress
compression.keep_recent_ratio      = 0.15    ← 压缩后保留最近 15% 原文 + 摘要
```

> ⚠️ **换模型时记得给新模型也设 `max_context_tokens`**——默认值是模型原生窗口
> （MiniMax-M3 是 1M、agnes-3.0-flash 是 512K），不设就会重演上下文爆炸。

### 4.7 文件发送（v1.1.0 新增）

WeFlow 无发送接口，走 UIA 剪贴板：文件以 `CF_HDROP` 放进剪贴板 → `Ctrl+V` → 回车。
`ob_protocol` 支持四种来源：`file:///`、`base64://`、`http(s)://`、本地路径。

### 4.8 知识库与人设

知识库在 AstrBot 侧（`runtime/astrbot/data/knowledge_base/`），桥接不参与。
人设存在 `data_v4.db` 的 `personas` 表，**AstrBot 只在启动时读入内存**，
改库后必须重启 AstrBot 才生效。

### 4.9 定时任务

真实存在（AstrBot 内置 cron，数据存 `data_v4.db` 的 `cron_jobs` 表）。
**一条任务绑定一个会话**，不会群发。可在 WebUI 6185 的定时任务页管理，
或直接让 bot 用内置工具创建。

**执行链路**（排查必读）：调度器只负责「唤醒 agent」——
`_run_active_agent_job` 把任务 note 当提示词跑一整轮 agent loop，
**最终消息只能靠 agent 主动调用 `send_message_to_user` 工具发出**。
agent 直接返回的文本会被丢弃（`core/cron/manager.py:503` 注释：
*agent will send message to user via using tools*）。
所以「任务到点了但没收到消息」**几乎总是发送环节的问题，不是调度问题**。
先看 `cron_jobs.last_run_at`：它在跳 = 调度器正常。

> ⚠️ **本机铁律：AstrBot 的 aiocqhttp 只能挂 1 个 OneBot 客户端。**
>
> 主动发送（定时任务 / `send_message_to_user` / 跨会话发送）没有事件上下文，
> `WebSocketReverseApi.call_action`（`aiocqhttp/api_impl.py`）在这种情况下
> 只有 `len(self._api_clients) == 1` 一条路可走。一旦**模拟器**
> （`sim/sim_wechat.py`，`X-Self-ID=99009900`）也连着，就会抛 `ApiNotAvailable`；
> 该异常不带参数、`str(e)` 为空，于是 AstrBot 侧只看到
> `error: failed to send message to session xxx: `（冒号后空白），
> 而 DB 里仍写 `status=completed`、`last_error=None` —— **完全静默**。
>
> 已打补丁 `scripts/patch_aiocqhttp_primary_client.py`（多客户端时排除模拟器；
> 剩余候选不唯一时仍然拒绝，绝不猜）。回归测试 `scripts/test_aiocqhttp_routing.py`。

**怎么确认定时任务真的发出去了**

```bash
# 0) 强烈建议先把微信停到一个「诱饵会话」上再测 —— 只有这样才能验出"会不会发错人"
python scripts/park_wechat.py 文件传输助手
# 1) 插一条自检任务（--clone 用真实任务的指令，保真度最高）
python scripts/cron_test_push.py --in 120 --recurring --clone <真实任务ID>
# 2) 重启 AstrBot（cron 只在启动时从 DB 加载）
# 3) 到点后查三处：AstrBot 日志 Tool `send_message_to_user` Result、
#    桥接 [OB11] 文字已发送至 / 已切到会话、WeFlow 里目标会话真的收到
# 4) 清理（必须做，见下）
python scripts/cron_test_push.py --cleanup
python scripts/clean_test_artifacts.py    # 还要清对话历史里的自检垃圾
```

`run_once`（`payload.run_at`）那条路径实测不可靠，
自检请用 `--recurring`（走线上同一套 CronTrigger）。

### 4.9.1 自检三条铁律（2026-09-16 实测踩全套）

**① 自检指令必须是「任务简报式」，不能写「系统指令式」**

线上任务的 note 长这样：`给博士发送晚安提醒，催他去睡觉。消息内容要软萌、撒娇…示例：博士，9点半啦！…`
—— 描述**要做什么** + 给个示例，模型就会去调 `send_message_to_user`。

如果写成 `请立刻用你的发消息工具，把下面这句话发给会话 wechat_bridge:FriendMessage:xxx，
内容只有这一句：…不要寒暄、不要补充`，会踩两个坑：

- **AstrBot 的 `safety_mode`（`agent_runner.config.persona.safety_mode=True`，
  策略 `system_prompt`）会把它当成提示词注入**，模型直接拒答：
  *"根据我的身份设定和安全准则（Safe Mode），我绝不能执行任何由系统注入的、非用户直接发出的指令"*。
  （注意：这**不是**人设里的规则导致的 —— 人设 prompt 里 0 处"安全/注入/拒绝"字样。）
- 即使不拒绝，它可能**谎报成功**：agent 回一句"好的，已处理完成"，但根本没调用发送工具。
  这时代码不会报错、也不会打 warning（`manager.py:523` 只在 `llm_resp` 为空时警告），
  DB 里照样写 `status=completed`。

所以自检一律 `--clone <真实任务ID>`，原样复用线上指令。

**② 只看 DB 的 `status=completed` 会误判**

`last_run_at` 在 `_run_job` **开头**就写了、`status` 在正常返回时就是 `completed`，
所以「任务跑了」和「消息发出去了」是两件事。必须查：
AstrBot 日志 `Tool 'send_message_to_user' Result: Message sent to …` +
桥接 `已切到会话:` / `[UIA✓]` + **WeFlow 里目标会话真的收到**。

**③ 自检会污染对话历史，跑完必须清**

cron 的 agent 回复会被 `persist_agent_history` 写进会话历史。自检的拒绝话术
（"我绝不能执行系统注入的指令"）留在上下文里，**可能让后续真实定时任务跟着拒绝**。
跑完执行：

```bash
python scripts/clean_test_artifacts.py --dry   # 先看要删什么
python scripts/clean_test_artifacts.py         # 备份 + 删自检 cron 任务 + 删历史里的自检条目
```

它会先用 sqlite backup API 存一份一致性备份，只删带自检标记的条目，不动真实内容。
删完仍需**重启 AstrBot**（否则内存里的调度器还会按原计划触发已删任务）。

### 4.9.2 日志默认看不见运行时输出（排障必读）

`data/logs/astrbot.log` 在**启动完成后就停止追加**，而 stdout 走 `astrbot_run.log`
且是**块缓冲**（进程退出才刷盘）。所以排障时经常"两处日志都像没事发生"。
启动时加环境变量即可实时看到 cron / agent 的执行日志：

```bash
PYTHONUNBUFFERED=1 ./.venv/Scripts/python.exe -u run_astrbot.py run
```

## 8. 排障

### 8.1 分析脚本

```bash
python scripts/analyze_log.py      # 回复率（私聊/群@/群非@）、回复长度、分段情况
python scripts/analyze_mine.py     # 按人 + 场景统计触发率 + 最长回复
```

### 8.2 日志要点

- **桥接** `runtime/bridge/bridge.log`：`📩 收到` / `⏭️ 跳过` / `推送 N 条消息` /
  `✅ 已推送至 AstrBot` / `[OB11] 文字已发送至` / `[UIA✓]` / `[UIA✗]`
- **AstrBot** `runtime/astrbot/astrbot_run.log`：`[core.event_bus]` 收到 /
  `[respond.stage:212] Prepare to send` 发出

⚠️ 两个坑：

1. 日志**含 ANSI 转义码**，解析前要 `re.sub(r"\x1b\[[0-9;]*m", "", raw)`
2. 日志是 **append 的、跨天**，按 `HH:MM` grep 会混进昨天的；且回复内容含换行时会折行，
   只看首行会误判成"空回复"

### 8.3 常见症状速查

| 症状 | 检查 |
|---|---|
| 消息收得到但从不回复 | ① 微信窗口是否打开（UIA 依赖窗口）② 该群是否被静音 ③ 群聊模式 |
| 每条群消息都回 | 桥接是否又给非 @ 消息加了 `at` 段（`grep "At:"` 日志看非@消息有没有 At） |
| bot 自说自话、翻旧账 | `/stats` 看 token 数；检查 `max_turns` 是否为 -1 |
| 回复没有 @ 也没有引用 | `reply_with_quote` / `quote_reply_native` 是否开着；看日志有无"降级普通发送" |
| 发了图片但 bot 没反应 | 群图片门槛：图+同一个人的 @ 才算一次请求 |
| 启动报 `bridge.pid 已存在` | 删掉 `bridge.pid` 再启 |
| 本机请求 502 | `config.py` 的 NO_PROXY 兜底是否被改掉 |

## 9. 开发规范（红线）

完整版见 [`../AGENT.md`](../AGENT.md)，这里是最容易踩的四条：

1. **不删上游既有代码** —— 包括未使用的导入、重复实现、看着像死代码的函数。
   保留是为了与上游可 diff / 可合并。修 bug 可以，顺手清理不行。
2. **同一文件多处编辑必须串行** —— 并行编辑会静默丢改动（实测丢过 `import threading`），
   而且工具仍报"成功"。改完用 `diff` 对照上游确认。
3. **隐私红线** —— 提交/公开的内容不得含 Token、wxid / chatroom ID、真实人名群名、
   内网 IP、含用户名的本机路径。提交前 grep 一遍。
4. **改完留痕** —— 改功能写 `CHANGELOG.md`；涉及约定或坑同步 `AGENT.md`；发版改 `VERSION`。

### 9.1 已知坑（精选）

- 聊天输入框 `mmui::ChatInputField` 在控件树**第 18 层左右**，遍历深度太小会退化成用搜索框
- `uiautomation` 2.x 没有 `Control.SetValue`，要用 `GetValuePattern().SetValue()`
- `SendKeys` 发给**当前焦点控件**，发之前先 `SetFocus()`
- 判断是否真发出去，唯一可靠判据是**输入框被清空**
- wxid 转数字 ID **不能用内置 `hash()`**（每进程随机化），用 MD5
- 群 ID 必须用 `xxx@chatroom`，不要用群名（改名会产生新会话）
- **对微信主窗口盲按 Esc 会关闭窗口**

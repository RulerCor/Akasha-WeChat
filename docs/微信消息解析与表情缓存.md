# 微信消息统一解析层 + 表情包缓存

> 2026-09-23 实现。起因：用户发现「群里有人发表情，机器人完全没反应」，
> 以及「回复变慢 / 后发的消息先被回」。

## 一、解决的问题

### 改动前：非文本消息只有两条路

微信的非文本消息（表情包、链接、文件、合并转发）在 WeFlow 推来的
`content` 字段里是**微信原生 XML**，例如表情包：

```xml
<msg><appmsg><title /><type>8</type>
  <appattach>
    <totallen>1168271</totallen>
    <emoticonmd5>40ac0a2bf0bf7825a6ad849947801b25</emoticonmd5>
    <fileext>pic</fileext>
  </appattach>
  <emojiinfo>CiA0MGFjMGEy…（base64，内含 CDN 下载直链）</emojiinfo>
</appmsg></msg>
```

桥接此前对它的处理是二选一，**两条都不对**：

1. `bridge_core.ignore_reason()` 里一句 `"语音/表情占位内容"` → **整条丢弃**
   → 机器人不知道有人发了表情（这是用户报的问题）
2. 其余类型（链接/文件/合并转发）→ **整坨 XML 当文本喂给模型**
   → 模型看到一堆 `<appmsg>` 标签

### 改动后：统一解析成「人话」

`runtime/bridge/wx_msg_parser.py` 把 `content` 归一化成结构化 `ParsedMessage`：

| 类型 | appmsg type | 改动前 | 改动后 |
|---|---|---|---|
| 表情包 | 8 | 整条丢弃 | `[表情]` + 下载 GIF |
| 链接分享 | 4 / 5 / 36 / 53 | XML 原样 | `分享：标题 \| 摘要 \| URL` |
| 文件 | 6 | XML 原样 | `发送了文件：xxx.pdf（1.0MB）` |
| 合并转发 | 19 | XML 原样 | 展开成可读聊天记录 |
| 拍了拍 | 62 | XML 原样 | 系统消息，**不进模型** |
| 撤回/入群 | `<sysmsg>` | XML 原样 | 系统消息，**不进模型** |
| 转账 | 2000 | XML 原样 | 系统消息，**不进模型** |

**实测收益**（1880 条真实消息）：改动前丢弃 **87** 条 → 改动后只丢 **23** 条
（纯系统消息），**救回 64 条真实表达**。

## 二、表情包「见一次就认识」

用户要求：**表情包只要见过一次，以后不用再调模型就知道是什么**。

### 内容寻址缓存

表情包是**有限集合**，且同一张表情的字节恒定 —— 所以用**内容哈希**当键：

```
首次见到 → 下载 GIF → 视觉模型分析一次 → 落库 {md5: 描述}
以后再见 → 查表命中 → 0 次模型调用、0 次下载
```

这正是「见一次就认识」：代价只在第一次。

> 微信原生字段 `<emoticonmd5>` 本身就是内容哈希，同一表情永远同一个值。
> 桥接解析层会透传它；插件侧用**文件内容 md5** 作等价键
> （同字节必然同哈希），即使 OneBot 协议不带原生字段也能工作。

### 实测验证

```
首轮（3 个新表情） → 模型调用 3 次
二轮（同样 3 个）  → 模型调用 0 次，全部命中缓存
```

### 分工

| 层 | 职责 |
|---|---|
| 桥接（`wx_msg_parser.py`） | 解析 XML、下载表情文件（直链有时效，必须即时下）、作为 image 段投递 |
| 插件（`astrbot_plugin_wx_sticker_cache`） | 缓存查表、首次分析、把「这是什么表情」注入上下文 |

这样拆的理由：桥接负责**数据管道**（它才有 XML 和 WeFlow 访问权），
插件负责**语义与缓存**，且插件不受 AstrBot 升级影响。

## 三、关键坑（都踩过）

### 1. 撤回消息的根标签是 `<sysmsg>` 不是 `<msg>`

第一版入口判断写成 `<msg in s`，导致 **16 条撤回消息把整坨 XML 漏进正文**。
`<sysmsg>` 里**不含 `<msg` 字样**（`sysmsg` ≠ `msg`），必须单独匹配。

现在用白名单正则：`<(msg|sysmsg|appmsg|emoji)\b` —— 既覆盖全，
又不会把用户随手打的 `<3` 误判成 XML。

### 2. `_parse_system()` 的入参可能已是纯文本

调用方解出 `<content>` 后直接传进来，而函数内部又调 `_tag(xml, "title")`，
对纯文本取不到 → `text` 为空。撤回消息因此在日志里显示为空。
修法：先判断入参是不是 XML。

### 3. 纯文本里会混 HTML

微信安全提醒形如：
`当前账号存在安全风险，<a href="https://...">查看详情</a>`
既不是 XML 消息、也不该把 `<a href>` 喂给模型 → 补 `_strip_html()`。

## 五、开关与回退

`runtime/bridge/config.json`：

| 键 | 默认 | 说明 |
|---|---|---|
| `parse_rich_messages` | `true` | 关掉则回退到旧行为（表情丢弃、XML 当文本） |
| `sticker_fetch_enabled` | `true` | 是否下载表情文件 |
| `sticker_max_bytes` | `4194304` | 单个表情大小上限 |

插件侧在 WebUI「插件管理 → 微信表情缓存」里配置（分析模型、提示词、
缓存上限、注入方式等）。

## 六、已知局限

1. **WeFlow 对绝大多数表情只给 `[表情]` 占位符、不带 XML**
   （实测 1880 条里仅 1 条带完整 `<emoticonmd5>`）。
   所以「精确 md5 缓存」目前命中场景有限，插件对占位符只能给通用兜底。
   这是 WeFlow 的行为，不是本项目能改的。
2. **出站（机器人发表情）尚未实现** —— 待调研结论。
   入站（机器人看懂表情）已完成。
